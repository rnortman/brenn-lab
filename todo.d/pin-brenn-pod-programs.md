brenn-lab does not build brenn-pod's two programs, the recorder `pod-capture` and the reader tool `frame-log`: the capture role is handed the recorder's location by the lab configuration, the default check tests it against a stand-in that replays recorded output of the real recorder, and no hardware-lane test records from a device through it. Both programs have been built under this repository's pinned toolchain through crate_universe git specs, each in a hub of its own, with no host program in any target-side action; `pod-capture` needs the build scripts of `build-id` and `alsa-sys` switched off, the build commit and its two companion values given as `rustc_env`, and `-ldylib=asound` as a rustc flag, since `alsa-sys`'s script otherwise reads the host's pkg-config. The brenn-pod revision that holds both programs is on a branch of brenn-pod's public remote and not yet on its `main`; a pin names a revision that must stay reachable there.

What waits on this: the reader tool in the default check, and with it alignment and the run-validity checks, which read captures; and the hardware-lane test below. The capture role and playback do not wait.

Done when `MODULE.bazel` pins brenn-pod by revision from its public remote, both programs build from it, `make repin` covers the new hubs, something holds the pinned revision and the declared build commit equal, the capture role on the runner's own machine can take the pinned recorder while the lab configuration can still name a recorder installed on any machine, a hardware-lane test records from an attached device through the capture role and asserts what it expects of the device, and the recorded transcripts the stand-in replays have been taken again at the pinned revision. On linux aarch64 no sysroot is pinned, so the link there takes the host's libasound; say so beside `aarch64-gate-tools-link-host-libc` when the pin lands.
