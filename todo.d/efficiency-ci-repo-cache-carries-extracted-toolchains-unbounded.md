The CI repository cache holds more than fetched archives. CI sets `--repository_cache=$HOME/.cache/bazel-repo`, and Bazel's repo contents cache defaults to `{--repository_cache}/contents`, so every reproducible external repository, fully extracted, is saved with the archives it came from: the LLVM toolchain's extracted tree is about 12 GB (about 2 GB compressed) beside its own release archive, and the Rust toolchains, sysroot and Python interpreter add more. The contents cache's GC acts only after `--repo_contents_cache_gc_idle_delay` (five minutes by default) of server idleness, which `make check` never leaves, and the bare `bazel-repo-` restore key carries every earlier generation across a pin change, so each toolchain bump adds a full extracted tree to every later entry. Choose and implement a bound in the workflow: for example move the contents cache outside the cached path (`common --repo_contents_cache=` with another path, or empty to disable it) so only archives are saved, at the cost of extracting every repository on each run; or drop the bare restore key so a pin change starts a fresh repository cache, at the cost of refetching everything after any `MODULE.bazel` edit. Measure a few real runs (entry size, restore and save time, extraction time) before choosing. Done when the saved repository cache's size is bounded by something the workflow does. These cache steps were adapted from the CI workflow of <https://github.com/rnortman/dorfq>, which caches the same repository-cache path under the same bare restore key, with the same Bazel version and the same pinned LLVM toolchain, so whatever bound is chosen here is owed there too. That is a statement about its configuration; its cache was not measured. The comment sits above the cache steps in `.github/workflows/ci.yml`.
