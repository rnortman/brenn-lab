The hardware-lane tests of the capture role run the pinned recorder, which loads the host's `libasound.so.2` at run time; the build links against the pinned sysroot's copy and ships none. That narrows the rule that nothing in a build or test action reaches for a host-installed program: a lane test that records, and only such a test, needs the host's ALSA runtime library. The default check builds the recorder and never runs it. It was chosen because a sound device's driver, ALSA configuration and plugins are the host's, and a pinned library reading the host's configuration and loading the host's plugins is a pairing nobody tests. The owner's question: may a lane test load the host's ALSA runtime? If yes, the sentence in `AGENTS.md` stands, and this entry and its comment are deleted. If no, the recorder's runtime library is brought in through Bazel and travels with the test, the lane tests are shown to pass with it on the workstation's ALSA configuration, and the lanes' prerequisite is removed from `AGENTS.md`. Until the owner has ruled, no other build or test action may load a host library on the strength of this exception. On linux aarch64 the build also takes the host's ALSA development files; that is `aarch64-gate-tools-link-host-libc`.
