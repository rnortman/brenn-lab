The lane tests that record, play or drive the playback role's ALSA code without playing, and the experiment runner hosting a capture role with the pinned recorder or a playback role, load the host's `libasound.so.2` at run time. For recording it is the pinned recorder that loads it; for playing it is the runner's own interpreter. The build ships none, and the default check loads none. That narrows the rule that nothing in a build or test action reaches for a host-installed program. It was chosen because a sound device's driver, ALSA configuration and plugins are the host's, and a pinned library reading the host's configuration and loading the host's plugins is a pairing nobody tests. Playing was added while this question was open, with the owner's agreement that it load this one library, because nothing can play without the library and the load sits in one module. The owner's question: may they load the host's ALSA runtime? If yes, `AGENTS.md` stands, and this entry and its comments are deleted. If no, the library is brought in through Bazel for the recorder and for the playback role, both lanes are shown to pass with it on the workstation's ALSA configuration, and the prerequisite is removed from `AGENTS.md`. Until the owner has ruled, no build or test action may load any other host library, or this one for any other purpose, on the strength of this exception. On linux aarch64 the build also takes the host's ALSA development files; that is `aarch64-gate-tools-link-host-libc`.
