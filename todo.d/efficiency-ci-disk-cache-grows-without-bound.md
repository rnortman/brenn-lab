The CI disk cache only grows. Each run restores the newest saved disk cache (falling back to the bare `bazel-disk-` prefix across pin changes), adds its own action outputs and saves the whole directory under a new key, PR runs included. Nothing removes an entry: the size and age limits in the tracked `.bazelrc` act only after the Bazel server has been idle for `--experimental_disk_cache_gc_idle_delay` (five minutes by default), and `make check` never leaves it idle. Every saved entry is therefore at least as large as the last, carrying the outputs of every earlier pin set, and all of them draw on the repository's shared Actions cache quota. Choose and implement a bound in the workflow: for example save the disk cache only from `main` (separate restore and save steps), drop the bare restore key so a pin change starts a fresh cache, or trim entries Bazel has not touched in the run before saving; and decide whether CI keeps its own disk-cache path or caches the tracked one. Each option trades run time against cache size, so measure a few real runs (entry size, restore and save time, cold-run time) before choosing. Done when the saved disk cache's size is bounded by something the workflow does. These cache steps were adapted from the CI workflow of <https://github.com/rnortman/dorfq>, which saves and restores its disk cache the same way, under the same bare restore key and the same garbage-collection limits, so whatever bound is chosen here is owed there too. That is a statement about its configuration; its cache was not measured. The comment sits above the cache steps in `.github/workflows/ci.yml`.
